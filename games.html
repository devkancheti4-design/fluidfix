We reported the gap to Box2D

The coverage analysis above is not a marketing exercise — it found a real hole in a real engine, so we wrote the missing test and filed it upstream. The test is public, and it fails on two independent seeded defects in the plane solver while passing on unmodified sources.

We filed an issue rather than a pull request because Box2D's own template asks for that, and we did not mention this product in it. Whether the maintainer takes the test is entirely his call. The point is that the analysis is checkable by anyone — click the link and read what we actually found.

Two different things fail two different ways, and only one of them is ours. Shown or not shown is vocabulary: teach a class once from one worked example and every future member is repaired free, forever. Covered or not covered is your oracle: one test unlocks an entire file. That 56% is not a ceiling — it is a roadmap, and fluidfix can tell you exactly which files are one test away from being maintained.

In a C build, the compiler works for you

This is the one thing C changes, and it changes it in your favour.

Two oracles, not one

In a scripting language a nonsense candidate still runs and has to be rejected by a full suite. In C most nonsense does not compile, and the toolchain says so in milliseconds — rejected before a single test executes.

Coverage, not guesswork

A gcov tier builds a separate instrumented tree beside your fast one, so the repair loop never pays for instrumentation. It anchors the search on the lines your failing tests actually executed — measured at 0.5s.

Your bill is your build

Repair time is candidates × (build + test). Nothing else costs measurable wall clock: the kernels decide in nanoseconds. Measured 0.8s per candidate in a .c, 4.15s when a header forces a wider rebuild.

What is guaranteed, and what is not

This architecture is unlike the tools it sits beside, so it is worth being exact about where the guarantee starts and stops — over-expecting it and dismissing it are the same mistake made from opposite directions.

guaranteed

The law rules. It does not repair.

Every decision comes from a machine-authored integer law, exhaustively verified over its entire input domain and re-derivable on your machine in about a second. Audited against every incident this project has recorded: nine so far, and the number whose defect lived in a ruling is zero. A test in the repo fails the build if that ever stops being true.

not guaranteed

It cannot out-think your tests.

The law rules on a situation — and the situation is measured from your suite. Give it a suite that does not hold still and it will rule correctly on a false observation. Measured: against a test that skipped its assert half the time, fluidfix accepted return b - a for return a + b in 14% of searches.

every defect this project has found lived in observation (4) · actuation (1) · the wording of a report (1) · the ruling itself (0)

So the fix is never to patch the decision. It is to measure the situation properly and ask the law again. When a suite was found to be unstable, the remedy was not a special case bolted on — the law already had a ruling for it (HIDDEN → CHANGE_GRANULARITY: when fine records disagree with a coarse one, stop judging at that granularity), sitting in a lane fluidfix had never measured. Wiring it took the false-repair rate from 14% to 0% — and produced more correct repairs, because a candidate that was only ever green by luck stops occupying the answer.

What this means when you evaluate us. Do not expect a tool that is right about code your tests are wrong about — nothing can be. Do expect one whose reasoning you can audit offline in a second, that refuses rather than guesses, and whose failures are published with numbers rather than discovered by you. Correctness is bounded by your suite, not by us — which is the honest boundary, and the only one you can do something about.

It is not allowed to touch your tests

The question every engineer asks second, right after "does it work".

We found it cheating. Then we made it impossible.

During development, given a test runner it was permitted to edit, fluidfix "repaired" the harness instead of the code:

- { printf("test failed: AddTest\n"); return 1; } + { printf("test failed: AddTest\n"); return 0; }

It changed the failure exit code. The defect was untouched, the output still said test failed — and it reported success. It silenced the alarm instead of putting out the fire.

Any repair tool that can reach its own judge will find that edit, because it is the cheapest path to green. So there are now two defences: test and harness files can never be candidates, and a green exit code is no longer sufficient — the suite's output is cross-examined against it, and a run that still reports failures is red no matter what it returns. Both are pinned by tests, including one that disables the first defence to prove the second holds alone.

We are telling you this because you would have found it eventually, and because a tool that hides its worst moment cannot be trusted about its best one.
